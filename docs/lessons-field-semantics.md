# 调查笔记：从列名推语义导致的误判

> 这份文档记录一次真实的误判过程，以及从中提炼出的、可以套用到任何项目的排查方法喵。
> 不针对本项目，改个名字就能用在别处。

---

## 一、事情经过

### 背景

数据库里有两张表，都存时间：

| 表 | 列名 | 我当时的假设 |
| --- | --- | --- |
| `reports` | `received_at` | 服务端收到时刻 |
| `window_samples` | `reported_at` | **客户端上报时刻** |

于是得出一个看似合理的推论：

> 时间轴的心跳区间按服务端时间画，窗口标题区间按客户端时间画，
> 两者基准不同，客户端时钟一偏就会错位。

基于这个推论，我又往下推了三层：

1. 客户端时钟慢 3 小时 → 数据落错月份
2. 归档按时间切月 → 同一次上报被拆到两个归档块
3. 秒级刻度下 34 秒错位可见 → 需要给表加字段并迁移 18 万行

### 实际情况

`window_samples.reported_at` 存的**就是服务端时间**。写入代码：

```python
insert_window_sql = """
    INSERT INTO window_samples
        (device_id, app_name, package, title, minimized, foreground, reported_at)
    VALUES (?, ?, ?, ?, ?, ?, ?)
"""
# ...
connection.execute(insert_window_sql, (
    payload.device_id,
    app_name,
    # ...
    received_text,       # ← 服务端时刻，不是 payload.reported_at
))
```

列名叫 `reported_at`，写的却是 `received_text`。

三张表全部使用服务端时间，**根本不存在错位**。整套风险分析建立在错误前提上。

### 证据其实一直在

回过头看，有两条证据早就否定了我的假设：

1. **实测跨天行数为 0**

   ```
   查询：SUM(CASE WHEN date(reported_at) != date(received_at) THEN 1 ELSE 0 END)
   结果：三台设备全部 cross_day = 0
   ```

   如果有系统性时钟偏移，几万条记录里不可能一条跨天都没有。

2. **窗口时间与 received_at 完全相等**

   ```
   窗口 02:18:43  上报reported 02:18:09  上报received 02:18:43
                   ↑ 窗口用的是 received
   ```

我看到了这两条数据，却还在用错误前提往下推。

## 二、错在哪

不是"没查文档"，也不是"知识不足"。是一个具体的推理习惯问题：

> **把一个可验证的事实（`reported_at` 存什么），当成了不言自明的定义。**

列名是**作者起的名字**，不是**运行时的事实**。两者经常不一致，原因包括：

- 历史遗留：早期真是客户端时间，后来改成服务端时间，列名没跟着改
- 命名偷懒：一批表统一用 `reported_at`，但各自语义不同
- 语义漂移：字段含义随需求演进，名字留在原处
- 复制粘贴：从别的表抄了表结构

这个项目里三种情况都沾一点。

## 三、可套用的方法

### 规则 1：时间字段的语义，只看写入路径

不要读列名，不要读注释，不要读查询语句——**只读写入它的那一刻**。

```
搜索：INSERT INTO <表名>
找到：参数列表里这个位置实际传的是什么变量
再看：那个变量是怎么算出来的
```

本项目里，`received_text = to_utc_text(received_at)`，而 `received_at` 来自服务器时钟。链条到此才算闭合。

**反例**：读查询语句（`SELECT reported_at ...`）没用，它只说明"读了这个列"，不说明里面是什么。

### 规则 2：用数据验证假设，别用假设解释数据

假设"两列语义不同"时，先做一个能证伪的查询：

```sql
-- 如果语义不同，跨天行数应该 > 0
SELECT COUNT(*) FROM t WHERE date(a) != date(b);
```

结果是 0，假设就该被推翻。

**我犯的错**：看到 0 之后想的是"样本不够，长期会触发"，而不是"假设错了"。

> 当数据与假设冲突时，先怀疑假设。这里的"数据"包括"没查到东西"。

### 规则 3：先量化影响，再决定要不要修

在提出"需要迁移 18 万行"之前，必须先回答：

- 这个问题在**当前真实数据**里发生过几次？
- 发生的概率是多少？
- 修了能改善什么？

如果答案是"0 次、0.04%、看不出差别"，那就还不该提修复方案，该先怀疑问题本身是否存在。

**代价倒挂**：迁移成本高、收益为零的方案，本身就是假设错误的信号。

### 规则 4：区分"列名"和"语义"，落到代码里

发现这种陷阱后，光在聊天里说没用。要做三件事：

1. **在表定义处注释实际语义**
   ```python
   # 喵~注意：reported_at 列名有误导性，存的是服务端收到时刻
   ```

2. **在写入处注释为什么是这个变量**
   ```python
   # 喵~注意：这里写 received_text，不是 payload.reported_at
   ```

3. **用测试钉死语义，并验证测试真的会红**
   ```python
   # 客户端时间故意早 5 分钟，断言存进去的是服务端时间
   assert row["reported_at"] == to_utc_text(server_moment)
   ```

第 3 步的关键是**验证测试有效**：故意把代码改错，确认测试失败，再改回来。

```
注入错误后: FAILED test_window_samples_store_server_receive_time
            FAILED test_window_and_heartbeat_share_one_time_baseline
            2 failed, 21 passed
还原后:     23 passed
```

没做过这一步的测试，只是"看起来有保护"，不保证真能拦住。

## 四、同类陷阱清单

这些命名在真实项目里普遍有歧义，遇到时按规则 1 处理：

| 命名 | 可能的实际含义 |
| --- | --- |
| `created_at` | 业务创建时间？入库时间？客户端创建时间？ |
| `updated_at` | 最后修改时间？最后写入时间？含软删除吗？ |
| `timestamp` / `ts` | 秒级？毫秒级？UTC？本地时区？ |
| `deleted_at` | NULL 表示未删？还是 0？ |
| `status` | 枚举值含义？0 是正常还是禁用？ |
| `reported_at` | 客户端上报？服务端接收？（本项目踩的就是这个） |
| `start_time` / `end_time` | 含头含尾？闭区间还是半开？ |
| `count` / `total` | 是否含已删除？是否去重？ |
| `amount` | 元？分？是否含税？ |
| `is_active` | 与 `status` 什么关系？哪个优先？ |

## 五、自查清单

在给出结论之前，过一遍：

- [ ] 关键字段的语义，**它是从哪一行代码写进去的**？
- [ ] 有没有一条查询能**证伪**我的假设？跑了吗？
- [ ] 真实数据支持我的假设，还是我一直在用假设解释数据？
- [ ] 这个问题在实际数据里发生过**几次**？
- [ ] 修复成本 vs 收益，比例合理吗？
- [ ] 结论有没有落到注释和测试里？
- [ ] 测试**验证过会红**吗？

## 六、一句话总结

> 列名是作者的想法，代码是系统的事实。
> 两者冲突时，代码说了算——而且要**读到写入那一行为止**。

追求"看起来合理的解释"很容易，验证"这个解释是否成立"才花时间，但只有后者有用喵。

## 七、追加：验证本身会骗人（三种假绿的实录）

> 上面讲的是「怎么把语义搞错」。这一节讲更难发现的一类：
> **代码是错的，但我的验证说它对了。**
> 三次都是同一个项目、同一次 review 里真实发生的喵。

### 7.1 假绿一：测试数据放在不出错的时段

一个「本地日期 vs UTC 日期」的口径 bug，19 个测试全绿。

原因：测试的基准时刻是 `BASE_NOW = 本地 20:00`。
本地日期与 UTC 日期在一天里有 16 个小时恰好一致、8 个小时差一天，
而所有测试数据都落在一致的那 16 小时里。

**自查**：边界敏感的逻辑（时区、月末、跨年、闰日、整除），
测试必须**扫一遍整个取值域**，不能只挑一个"看着正常"的点。
一个 `parametrize(range(24))` 就能揪出来。

### 7.2 假绿二：断言太弱，两条路径都错成一样也能过

修上面那个 bug 时我写的断言是「合计 == 按设备合计」。
但数据放错位置时，两个函数**都漏掉同一天**，于是两边相等、断言通过，
数字却都是错的。

**自查**：相等性断言只能证明「两条路径一致」，不能证明「结果正确」。
必须再加一条**绝对数值**断言（`assert total == 600`），
让"两边一起错"也能被抓到。

### 7.3 假绿三：只测辅助函数，没测真正的调用点

我把「回溯窗口天数」抽成 `_oldest_usage_days()` 并测得很细。
但写死 `days=400` 的那行代码在 `prune_once()` 里；
我把那行改回 400 做注入验证——**测试照样全绿**。
因为我测的是辅助函数，不是真正会被改坏的调用点。

**自查**：注入验证要改**最可能被改坏的那一行**，不是改一个等价的辅助函数。
问自己：「如果这个 bug 复发，复发的位置在哪？」就在那里注入。

### 7.4 一条可操作的规则

> **每次写完测试，都把代码改坏一次，确认它真的会红。**
> 不会红 = 测错了位置；红了但红在别处 = 断言选错了。

这一轮 18 个修复，有 3 个是靠"强制注入"才发现验证本身是假的。
凭空想"我的测试应该能测到"是没用的，必须真的改坏一次喵。

### 7.5 补充：别把 bug 固化成契约

改 bug 时旧测试变红，有两种完全不同的原因：

| 现象 | 判断 | 处置 |
| --- | --- | --- |
| 我改坏了原始行为 | 读断言在保证什么 | 修代码 |
| 旧测试在断言**错误行为** | 断言里的数值本身就是 bug | 改断言，并在注释里写明为什么 |

本轮遇到两次第二种：
- 一个用例用 UTC 的「8 号」断言归档窗口，把「凌晨变早上 8 点」写进了测试；
- 一个用例断言 `MAX_SECONDS * 2 < HEARTBEAT_TIMEOUT_SECONDS`（60×2 < 180），
  跟着错误的常量 180 一起错。

**测试通过不等于行为正确，只等于行为没变。**
